Your APIs and databases. Agent-ready.

mcp-forge turns HTTP and GraphQL endpoints, SQL queries and NoSQL operations into curated MCP tools for Claude and other agents. You decide which tools exist, what they are called, and exactly what comes back.

Built for

The moment an agent needs real data, and you need control.

  • Support

    “What did this customer order?”

    Publish one read-only query with a typed customer id. Emails stay masked, results stay under the row limit, and the agent never sees a table you didn't allow.

  • Platform teams

    Internal APIs, with a person in the loop

    Import the spec, keep the twenty operations that matter, and require approval on anything that changes data. Each client gets its own access key.

  • Data and analytics

    Let agents explore, not wander

    Turn on list, describe and run-SQL for a warehouse, limited to the tables you name. Every statement is parsed first and runs read-only with a time limit.

Curate, don't dump

One API answer is a hundred fields. Your agent needs three.

Each tool gets a name and a description written for the model, typed parameters, and an optional jq response shape. Agents see the fields that matter, spend fewer tokens, and pick the right tool more often.

  • Rename tools, hide parameters, give them fixed values
  • Shape responses with jq before the agent sees them
  • Re-import when the spec changes; your edits are kept
  • Hundreds of operations? Offer search_tools and call_tool instead

New tools, databases, auth configs, resources, prompts and keys open in a dialog with numbered steps. Next asks the server about the step first, so a mistake is caught where you made it.

You describe

# endpoint https://api.github.com/graphqlquery Repo($owner: String!, $name: String!) {  repository(owner: $owner, name: $name) {    stargazerCount  }}

The agent sees

repo(owner, name)→ owner = "rust-lang", name = "rust"{"repository": {"stargazerCount": 104000}}

Each $variable becomes a typed argument. Values travel as GraphQL variables, never pasted into the document. Import a whole schema by introspection if you prefer.

You describe

# MongoDB · shop · read onlyfind orders{"filter": {"customer": "{{customer}}",            "status": "{{status}}"}, "limit": 20}

The agent sees

orders_for(customer, status)→ status = {"$ne": null}refused: status takes a string, not an operator

Each {{name}} is a typed argument that fills in a whole value, never an operator or a key. $where never runs, and allowed names, masked fields and row limits apply to every NoSQL tool.

You describe

user_overview(login) 1 get_user  {login: .input.login} 2 repos     {owner: .steps[0].login} output    {name: .steps[0].name, repos: .last | length}

The agent sees

user_overview(login = "ada")→ two requests, one answer{"name": "Ada Lovelace", "repos": 12}

A chain calls other tools of the project in order, with jq between steps. The agent makes one call; the Calls tab shows every step, and a failing step stops the chain.

Get started

From nothing to a working tool in five minutes.

  1. Install

    One command on macOS, Linux or Windows, or the Docker image.

  2. Start and sign in

    Run mcp-forge serve, open 127.0.0.1:7410, and create your account with the setup code from the log.

  3. Add or import tools

    Describe a request, import a spec, or connect a database, then try it in the test console.

  4. Connect your agent

    Copy a snippet from the Connect tab and ask Claude a question. It calls your tool.

curl --proto '=https' --tlsv1.2 -LsSf https://github.com/jaydip187/mcp-forge/releases/latest/download/mcp-forge-installer.sh | sh
powershell -ExecutionPolicy Bypass -c "irm https://github.com/jaydip187/mcp-forge/releases/latest/download/mcp-forge-installer.ps1 | iex"
git clone https://github.com/jaydip187/mcp-forge && cd mcp-forge
docker build -t mcp-forge .
docker run -d --name mcp-forge -p 127.0.0.1:7410:7410 -v mcp-forge-data:/data \
  -e MCP_FORGE_ADMIN_TOKEN="$(openssl rand -hex 24)" mcp-forge

The installers put mcp-forge in ~/.cargo/bin. Prefer a manual install? Download an archive from the releases page.

Databases

Read-only until you say otherwise.

Connect PostgreSQL, MySQL, SQL Server, SQLite or ClickHouse. Publish saved queries with typed :name parameters, and optionally let agents list tables, describe them and write their own SELECT statements. Values are always sent separately from the SQL, never pasted into it.

Mask sensitive columns such as users.password_hash or *.email, and limit which tables agents may explore.

MongoDB, Redis, DynamoDB and Elasticsearch connect the same way, with the same access modes, allowed names, masks and limits.

What agents may do on a connection
Access modeSaved queriesAgent-written SQL
Read only defaultreadread
Saved writesread and writeread
Full accessread and writeread and write

Every write runs in a transaction, is undone if it changes more rows than allowed (100 by default), needs a WHERE clause on UPDATE and DELETE, can be tried with dry_run, and lands in the audit log.

Security

Built to fail closed.

Agents get real access to your systems, so every SQL statement passes through independent layers. Each one is enough on its own to stop a write on a read-only connection.

  1. Database login. Use a login that may only SELECT. The Test button shows what yours can do.

  2. Read-only session. Reads run in a read-only transaction with a server-side time limit, then roll back.

  3. Statement check. SQL is parsed; exactly one statement is allowed and classified as read, write, schema change or admin. Writes hidden in CTEs are refused.

  4. Function blocklist. Functions that write, read server files, reach other servers or sleep, such as pg_read_file, dblink or LOAD_FILE, are refused.

  5. Limits. Row and time limits, a cap per cell, column masks, a table allowlist, and for writes the row cap, dry run and audit log.

Localhost only by default. Requests must carry a loopback Host header, which blocks DNS rebinding. Any other address requires an admin token.

Secrets are references. env:NAME or keyring:NAME, resolved at call time and redacted from errors, logs and exports.

Accounts done properly. argon2id passwords, HttpOnly SameSite cookies, CSRF header and sign-in backoff.

No lock-in

Your tools. Your machine. Your call.

mcp-forge is free and open source under MIT or Apache-2.0. It runs where you run it, connects only to the APIs and databases you configure, and exports every project as a plain tools.yaml you can keep in git.

FAQ

Questions

What is MCP?

The Model Context Protocol is an open standard that lets AI applications such as Claude call external tools. mcp-forge serves every project as an MCP server over streamable HTTP at /mcp/<project> and over stdio.

Which MCP clients work with it?

Any client that speaks streamable HTTP or stdio: Claude Code, Claude Desktop, and clients that read .mcp.json. Tool changes are pushed to connected clients, so you can keep editing while an agent is connected.

Where are my API keys and database passwords stored?

Nowhere. mcp-forge keeps references such as env:GITHUB_TOKEN or keyring:shop-db and resolves them each time a tool runs. Pasted secret values are refused, and tools.yaml exports contain only the references.

Can an agent change data in my database?

Only if you allow it on that connection. Schema changes need a separate switch, admin statements never run, and full access must be confirmed explicitly.

Does it send telemetry?

No. It only connects to the APIs and databases you configure, and to spec URLs you import on purpose.

Can I run it on a server for my team?

Yes. Bind to another address with an admin token, put TLS in front with a reverse proxy, and add accounts with mcp-forge user add. A Docker image is included.

Ready to put an agent on your API?

Install it, start mcp-forge serve, and point it at an API or database you already use.
